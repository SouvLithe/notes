# 关于Java
## 语法
Java是按值传递的。分为基本数据类型和引用数据类型。
Java没有严格意义上的指针，new关键字可类比C++指针申请的动态变量。
Java 通过**强制初始化、默认值、以及类型语义上的位屏蔽**，保证程序员永远看不到底层内存中“未使用位”上的历史残留数据，从而避免未定义行为和安全隐患。
Java不允许泛型数组。

可以推迟类型选择到我们声明一个变量或实例化一个变量。现代Java中，在实例化时不需要指定类型，右边<>不需要String类型
```sql
SLList<String> bone = new SLList<>("bone");
```

### 继承、接口&构造函数
x的超类是y，那么x的内存框就包含y，即当你创建一个 `X` 的对象时，这个对象在堆内存中的布局会 **包含 `Y` 中定义的所有实例字段**。
**`default` 方法**，允许在接口中提供方法的默认实现，即可以写方法体。这样既保留了接口的抽象特性，又方便了接口的演化，而不影响已有的实现类。
**注意事项**：
- `default` 方法可以被实现类覆盖，也可以被其他接口继承。
- 如果一个类实现了两个接口，且两个接口有相同的 `default` 方法签名，那么必须覆盖该方法解决冲突。
- `static` 方法也可以在接口中定义，但它不属于实例方法，与 `default` 不同。
子类有重载的，用子类的；没有@Override，则使用父类的
**接口继承是“签合同”，实现继承是“照抄作业”。**

覆盖方法的调用遵循两个简单规则：
- 编译器采取保守策略，只允许我们按照静态类型来操作。
- 对于被重写的方法（_不是重载方法_），实际调用的方法是基于调用表达式的动态类型。
- 可以使用类型转换来覆盖编译器的类型检查。

java中的构造函数，必须以调用父类的一个构造函数开始；如果你没有明确调用构造函数，编译器会自动默默帮你完成这个任务。
如果你不指定调用哪个超类的构造函数，它会调用没有参数的默认构造函数。
所有没有显式指明继承类的类，都会隐式继承Object类。

- **静态类型**：变量声明时的类型，决定了编译器允许你调用哪些方法。
- **动态类型**：变量实际指向的对象的类型，决定了运行时实际执行哪个版本的方法（多态）。
- **当把子类对象赋值给父类引用（向上转型）时**， **只能通过该引用调用父类中声明的方法**，即使实际对象是子类，也无法直接调用子类独有的方法

![[Pasted image 20251111143439.png]]
**方法返回类型的静态类型（编译时类型）决定赋值兼容性**
- 方法 `maxDog` 的声明是：`public static Dog maxDog(Dog d1, Dog d2)`  
    这意味着 **无论你传入什么子类对象（如 `Poodle`），方法的返回值编译时类型都是 `Dog`**。
- 当你把返回值赋值给一个子类变量（如 `Poodle largerPoodle = ...`）时，编译器会检查：右边表达式的静态类型是 `Dog`，左边是 `Poodle`，而 `Dog` 不一定是 `Poodle`（向下转型不安全），所以**编译错误**。
- 即使运行时返回的对象确实是 `Poodle` 实例，编译器也不允许直接赋值，因为它只认静态类型。

### 高阶函数
老版本的Java中不能包含指向函数的指针，所以不能使用函数式编程。Java是静态类型语言，需要检查类型，而当时没有函数这个类型。
替代方案是 **用接口继承“没有特定功能的函数式”**，然后实现哪个类，并重新一些原本未定义的方法。
```java
public static <T, R> R do_twice(Function<T, R> f1, Function<R, R> f2, T x)
```
被调用函数f1的输入类型是T，输出类型是R，传入高阶函数的参数名为f1；（f2同理）
该高阶函数定义了两个泛型类型，第一个是T，第二个是R ,就是`<>`中的，返回值类型为R

### 多态&高阶函数
java中的接口提供了回调功能，有一些语言通过显示传递函数来处理回调
- comparable表示：我想将自己与另一个对象进行比较。
- comparator表示：比较两个其它对象。
回调是指：**把一段代码（通常是函数或方法）作为参数传递给另一段代码，当某个事件发生时，这段代码会被“回调”执行**。

补充一个继承的知识点：
- 不能用 `super.super.something` 的方式来调用父类的父类
不允许链式 `super.super` 是因为：
1. **封装性**：父类可能对祖父类的行为进行了封装或修改，直接越过父类访问祖父类会破坏父类的封装。
2. **方法重写**：如果父类重写了祖父类的方法，`super.super.method()` 会跳过父类的重写逻辑，可能导致对象状态不一致。
3. **多继承问题（虽然 Java 是单继承）**：允许 `super.super` 会使继承链变得复杂，增加理解和维护成本。
4. **语言简化**：Java 刻意不提供此语法，鼓励你通过父类提供的接口来达到目的。

补充一个动态方法选择：
- 编译时，在其静态类型中查看有无合适的签名，若有则**锁定该签名**，否则 Compile Error
- 运行时，在锁定签名的前提下，再在其动态类型查找有无更合适的方法，若无，则进一步查询其父类

## 特性
**静态让步，动态兜底**指当使用**强转**时，编译器会运行其通过，但运行期JVM会进行一次动态
类型检查（checkcast指令），判断变量是否实际是强转后的类型。
分两次检查的原因：
1. 编译期要全局流分析时空消耗过大； 
2. 可靠性，避免编译时不通过运行时可以的假阴性； 
3. 向后兼容保留历史遗留的代码（raw类型，如`List` 而不是 `List<String>`）

Malamute frankSr = new Malamute("Frank Sr.", 100);  
  
Poodle largerPoodle = (Poodle) maxDog(frank, frankSr); // runtime exception!

## 并查集
不相交集数据结构，也翻译为**并查集**或**不相交集合**
不相交集合主要有两种操作：
- `connect(x, y)` ：连接 `x` 和 `y` 。又称为 `union`
- `isConnected(x, y)` ：如果 `x` 和 `y` 连接（即属于同一集合），则返回 true
![[Pasted image 20251205100432.png]]
以下是并查集主要应用场景：
- 动态连通性问题 - 判断网络中两个节点是否连通
- 图论相关 - 检测无向图中的环（合并每条边的两端点，如果合并前两个端点已经属于同一集合，则存在环）、连通分量计数（合并结束后，根节点的个数就是连通分量的个数）
- 等价类 / 分组问题 - 好友关系（两人是否在一个朋友圈）、图像分割（相邻且相似像素合并为一个区域）

## 树
### `BST，Binary Search Tree`
Hibbard删除法：找到当前节点的前继节点和后继节点。例，删除k
![[Pasted image 20251116192434.png]]
虽然此算法能正确工作，但在频繁的删除和插入操作后，会导致树的**高度增加，结构变得不再平衡，甚至可能退化**。
从实现二叉搜索树的视角来看，我们想要实现搜索和插入操作时，是直接明了的（左根右的顺序，没有额外维护的信号）；插入的时候要注意避免过度递归（过度递归导致栈爆炸，可用while代替）；删除操作更具挑战，典型的方法是混合删除（Hibbard删除法）。
### B-Trees
树的高度决定了查找节点的最坏情况运行时间。
B-Tree 是 **多路搜索树**，是BST的推广，**并不是BST**。
**3阶B树**（每个节点最多2个键，最多3个子节点）为例，插入 1~7 的过程：
```example
初始空
插入1: [1]
插入2: [1,2]
插入3: 节点超了，分裂，中间键2上提成为根
        [2]
       /   \
    [1]     [3]    

插入4: 找到叶子[3]，插入后[3,4] -> 未超
        [2]
       /   \
    [1]   [3,4]

插入5: 叶子[3,4]插入5变[3,4,5]超了，分裂，中间4上提到父节点
父节点[2]接收4变成[2,4]（未超）
        [2,4]
       /  |  \
    [1] [3] [5]

插入6: 叶子[5]插入6变[5,6]未超
插入7: 叶子[5,6]插入7变[5,6,7]超了，分裂，中间6上提
父节点[2,4]接收6变[2,4,6]超了，继续分裂，中间4上提成为新根
          [4]
         /   \
      [2]     [6]
     /  \    /  \
   [1]  [3] [5]  [7]
```
所以 B-Tree 是从 **下往上** 生长的，不像二叉搜索树从上往下长。这样保证所有叶子在同一层，树是 **绝对平衡** 的。

B-Tree 如何保持平衡？
B-Tree 的平衡靠的是 **节点分裂（split）** 和 **节点合并（merge）**，核心规则是：
- 每个节点最多有 **m** 个子节点（m 称为阶，如 m=4 是 4阶B树）。
- 每个节点最少有 **⌈m/2⌉** 个子节点（根节点可例外）。
- 所有叶子节点都位于 **同一层**。
在底部，永不加入新的叶子，而是向原有的叶子节点加入新叶子节点。当此结点的结点数量大于一个量时，选出一个添加至该叶子节点的根节点。

## Hashing
本质上，就是创建一个巨大的数组，然后访问与数组对应的适当元素。
**解决哈希冲突的两种主要方法**：
1. **链地址法（Separate Chaining）**——每个桶是一个链表（或树），称为“哈希桶”。
![[Pasted image 20251118155359.png]]
2. **开放寻址法（Open Addressing）**——冲突时寻找下一个空桶，没有额外的链表，也叫散列表。
```txt
哈希表数组（线性探测示例）
索引    内容
[0]   null
[1]   (keyA, valA)
[2]   (keyB, valB)
[3]   (keyC, valC)   // keyC 原本应放在索引2，但被占了，往后找到3
[4]   null
[5]   (keyD, valD)
...
```
注意+警告：
- 永远不要在hash集合或者hash映射中存储可以改变状态的对象。因为如果对象以某种方式改变，它的hash码也会跟着改变，可能会导致item丢失。
- 如果你重写了equals方法，那么你也必须重写hashcode方法。原因在于hash映射和hash集合在遍历桶中的项目时，使用equals方法来检查某个项目是否存在。

## heap
二叉最小堆：定义为一个二叉树它是  **完全性**，并且追寻 **最小堆属性**.
- **最小堆属性**：意味着每个节点都小于或等于它的两个子节点。
- **完全性**：这颗树只在底层缺少元素，并且所有存在节点尽可能地靠左。
删除最小堆地节点时，可以想象成一家公司，所有你可以想象x是一个新员工，你会把新员工放在最后一个位置，然后尽可能地提拔他。

#### Dijkstra 算法  
- 始终按距源点的总距离从小到大访问顶点
- 一旦某顶点被移出 PQ，其最短距离即已确定
- 松弛操作对已访问顶点（已出队者）不再生效
**Dijkstra算法一句话概括**：按从源点的最佳已知距离顺序访问顶点，访问意味着松弛该顶点的所有边。如果边的权重为非负，它保证能给你最优结果。

#### A*
**核心思想**：A*算法是**启发式搜索算法**，结合了Dijkstra算法的最优性保证和贪心搜索的效率。
A* = Dijkstra 的已知代价 g(v) + 启发式估计 h(v)，按总和 f(v)=g(v)+h(v) 排序访问顶点，兼顾“已走”和“离目标还剩多少”，先探最有希望的方向。
- `g(v)`：从起点到当前节点 `v` 的实际最短距离。
- `h(v)`：从 `v` 到目标节点的**启发式估计**（如直线距离、曼哈顿距离）。
- 每次从优先队列中取 `f(v)` 最小的节点扩展。

**核心要点是：启发函数必须足够优秀。衡量“优秀”需要满足两个定义：**

1. **可采纳性。** 启发函数值 heuristic(v, target) ≤ 节点 v 到目标的真实距离 $trueDistance(v, target)$。
2. **一致性。** 对于节点 w 的每个邻居节点 v：  
	$启发函数值 heuristic(v, target) ≤ dist(v, w) + heuristic(w, target)$  
	其中 $dist(v, w)$ 是从节点 v 到 w 的边的权重。

伪代码：
```text
* 初始化open_set和close_set；
* 将起点加入open_set中，并设置优先级为0（优先级最高）；
* 如果open_set不为空，则从open_set中选取优先级最高的节点n：
    * 如果节点n为终点，则：
        * 从终点开始逐步追踪parent节点，一直达到起点；
        * 返回找到的结果路径，算法结束；
    * 如果节点n不是终点，则：
        * 将节点n从open_set中删除，并加入close_set中；
        * 遍历节点n所有的邻近节点：
            * 如果邻近节点m在close_set中，则：
                * 跳过，选取下一个邻近节点
            * 如果邻近节点m也不在open_set中，则：
                * 设置节点m的parent为节点n
                * 计算节点m的优先级
                * 将节点m加入open_set中
```
特点
- **优点**：比 Dijkstra 快（尤其在大图、目标明确时）；保证最优性（启发函数满足可采纳性）。
- **缺点**：需要设计良好的启发函数；内存消耗仍较大（需存储所有待扩展节点）。

#### `D（Dynamic A*）`
主要用于**未知环境或环境动态变化**下的路径规划。强调**算无遗策**，即我的探索路径类似一个同心圆，在抵达目标的同时事实上我也找到了同心圆里面的其他结点的所有最短路径
核心思想
- 传统 A* 是静态规划：环境改变后必须重新从头搜索。
- D* 能**增量式地修复路径**：只更新受变化影响的局部区域，避免全局重算。
大致实现思路（以 D* Lite 为例）
```text
维护每个节点的 **rhs**（right-hand side，即从目标反向传播的估计代价）和 **g** 值。
使用优先队列按 **key = (min(g, rhs) + h, min(g, rhs))** 排序。  
**初始化**：从目标开始反向计算，类似于 Dijkstra 的反向版本。
**当边权变化（如发现障碍物）**：
    只更新受影响节点的 rhs 值。  
    将这些节点加入优先队列，重新计算。   
    只扩展局部变化区域，直到起点代价收敛。
```
特点
- **优点**：适合动态环境（地图变化、未知地形）；避免完全重新规划，效率远高于反复调用 A*。
- **缺点**：实现复杂；需要维护额外的信息（rhs、多源影响域）。

### Kruskal算法：
有个很好的特性，相对Prim好实现。
基本思路：假设已经以某种方式将所有边按照顺序排好了，逐一遍历这些边，并进行添加，只要它们不形成环。（伪装下执行割性质）
计算过程：
```text
1. 将所有边按权重升序排序。
2. 初始化并查集（每个顶点独立）。
3. 依次取每条边：
    - 如果边的两个端点不在同一集合，则加入MST，并合并两个集合。
    - 如果在同一集合，则跳过（会形成环）。
4. 当加入的边数 = 顶点数-1 时结束。
```

## P=NP
只要对以下三个问题中的**任何一个**找到**高效（多项式时间）解法**：
- 3SAT
- 独立集（INDSET）
- 最长路径（LONGEST-PATH）
就能立即得到一个**受时间/空间限制的高效压缩算法**。
原因：  
	“带时空限制的压缩问题”可以**归约**到 3SAT、INDSET 和 LONGEST-PATH 中的任意一个——也就是说，谁能快速解决它们，谁就能快速做最优压缩。
这句话的意思是：**最优压缩在计算难度上与 3SAT、独立集、最长路径等经典难题是等价的**。
	如果你能找到一个多项式时间算法来解决其中一个（例如快速判断一个字符串是否存在短压缩），那么你就能用同样的方法解决所有 NP‑完全问题，也就证明了 **P = NP**。反之，如果这些问题是困难的（普遍认为它们没有多项式时间算法），那么“带时空限制的最优压缩”也同样困难。
![[Pasted image 20251124222818.png]]
为什么它可以转换为最长路径问题？它是NP类问题。什么是NP类问题？
这其实就是两类可以回答yes或者no的问题：
- P类问题：能高效解决的问题。
- NP类问题：解放能高效验证的问题。如果给出一个解，可以很快地检查出它是否正确。

所有 NP 问题都能归约到 3SAT——  其中就包含“受空间/时间限制的压缩问题”。
换句话说，  
凡是“答案为‘是’时可在多项式时间内验证”的决定问题，  
都可以**在多项式时间内**转化成一个 3SAT 问题。

P=NP？，也就是说，可以高效验证的问题是否也能高效解决？
有很多不认可的：
- 如果这是真的，那么他就应该已被证实了。
- 创造问题的解决方案应该比验证解决方案更为困难。
![[Pasted image 20251124224624.png]]
事实证明，所有的NP类问题都可以彼此归约。如所有NP问题都可以归约到3SAT问题。
这种可以被相互归约的问题称为  **完全NP**  问题，
有趣的是，如果你解决了其中之一，就等于说解决了所有的完全NP类问题。

## 排序
Knuth的《计算机编程艺术》中定义排序为：重新排序或者置换你的项目，使得它们根据你的小于操作符按照非递减顺序排列。
要有一种感觉：事物不仅仅可以被排序或未排序，还有中间状态，即事物可以部分排序，可以使用 **逆序** 这个术语指代，也就是 **克莱默法则**。
**对排序目标的另一种表述：**  
	给定一个包含 Z 个逆序对的元素序列，通过一系列操作将逆序对的数量减少到 0。

---
### 选择排序
基本思路-找到最小的元素，将其放在最前面，然后固定（一旦放置，不再移动），不断重复这个过程，直到所有元素都被固定。
	时间复杂度是 O（N^2）

---
### 堆排序
选择排序的变体。**对 N 个元素进行堆排序：**
- 将所有元素插入一个**最大堆**，原输入数组可丢弃；准备一个输出数组。
- 重复 N 次：
  - 从最大堆中**删除最大元素**；
  - 将被删除的元素放到输出数组**当前未使用部分的末尾**。
![[Pasted image 20251122151655.png]]
- 将所有元素放入堆中：O(N log N) 时间。
- 选出最大元素：O(1) 时间。
- 每次删除最大元素：O(log N) 时间，共 N 次。
总运行时间 = O(N log N) + O(N) + O(N log N) = **O(N log N)**
内存占用：需要 **O(N)** 的额外空间来保存堆中的数据副本。 
可以通过一些“巧妙的小技巧”把这部分额外内存开销也省掉。
#### 原地堆排序
只需要使用原始的数组，不需要额外的空间。是一种原地将数组转换成堆的方法。
工作方式：遍历节点并以反层序同步它们，结果将会是一个堆。
自底向上堆化输入数组：
- 按**逆层序**对所有节点执行 sink(k) 操作。
- 只要 sink 完成，就能保证以位置 k 为根的子树已经是一个堆（蓝色部分）
![[Pasted image 20251122153428.png]]
从后向前遍历（17 --> 32依次遍历），组成了一个完整堆就标颜色。
![[Pasted image 20251122153524.png]]
![[Pasted image 20251122153358.png]]
如果你有两个子堆和一个顶部的任意值，并且你下沉那个值，整体结果是一个堆。
- 自底向上堆化：O(N log N) 时间。
- 选最大元素：O(1) 时间。
- 每次删除最大元素：O(log N) 时间。
空间复杂度是常数--因为所有的操作都是在这个数组上进行的。
内存复杂度是你额外使用的空间量。

1. 将数组分成两部分，对这两部分进行排序
2. 创建一个辅助数组，比较这两个数组中最小值的大小，并取最小的那个

- 逐个取出输入中的元素，将其**插入到输出序列中的正确位置**。

### 快速排序
快速排序的基本思路被称为：分区。
快速排序（Quicksort）是 Tony Hoare 为“分区排序”取的名字。  
在绝大多数实际场景中，它是经验上最快的排序算法。  
**快排把“比较 + 移动”的总工作量压到了理论下限的常数倍附近，而且所有操作都发生在顺序访问的缓存行里，CPU 缓存/分支预测几乎全程满速运转；其他排序至少缺其中一项。**

方法一：
- 从列表**右端开始扫描**。  
- 只要发现**更小的元素**，就把它插到**最左边的空位**；  
- 遇到**更大的元素则跳过**。
非常适合用**双端队列**实现
方法二：
依次待排序数组插入一棵 **BST（二叉搜索树）**，利用BST的特性排序
- 所有小的item在左子树
- 所有大的item在右子树
方法三：三路扫描
扫描三次数组，依次将小于该pivot（中心点）的、pivot、大于pivot的放入一个新的数组。
1. **选择 pivot**（例如取数组的第一个元素 `arr[0]`）。下面以升序为例：
2. **创建临时数组** `temp`，长度与原数组相同。
3. **第一次扫描**：遍历原数组，将所有 **小于 pivot** 的元素按原顺序依次放入 `temp` 的头部。
4. **第二次扫描**：遍历原数组，将所有 **等于 pivot** 的元素（或者只放一个 pivot，具体看是否需要处理重复值）放入 `temp` 的当前位置。通常只放一个 pivot，因为递归时会处理左右子数组。
5. **第三次扫描**：遍历原数组，将所有 **大于 pivot** 的元素按原顺序依次放入 `temp` 的剩余位置。
6. **将 `temp` 复制回原数组**（或者直接使用 `temp` 作为新的子数组继续递归）。
7. **递归**：对 `temp` 中小于 pivot 的部分和大于 pivot 的部分重复上述过程。

**那快速排序究竟有多快？**  --  需要计算**分区操作的次数与开销**。
理论分析：
- 一次分区耗时 **O(k)**，其中 k 是被分区元素的个数。
- 关键变数：**枢轴（pivot）最终落在哪个位置**，会直接影响整体运行时间
最期望时间复杂度是nlogn，最差`N^2`

- 完成快速排序所需的**平均比较次数**：≈ 2 N ln N
- 标准差：`√[(21 – 2π²)/3] N ≈ 0.6482776 N`

事实上，出现基准点选择导致的性能下降概率很小。

### 快排进阶
quicksort的核心在于分区，如果有个更贴切的名字，应该是分区排序。
如何避免快排最坏情况？
四种避免快排最坏情况的思路：
1. **随机化**：随机选枢轴，或排序前先把数组洗牌。可以伪随机，也可以真随机。
2. **更聪明的枢轴**：计算或近似中位数作为枢轴。
3. **自省**：递归太深时自动切换到更保险的排序算法（例如上限是5logn）。
4. **预处理数组**：事先分析数组是否会让快排变慢。但目前没有明显办法——仅检查“是否已排序”不够，因为“几乎有序”的数组也会让快排接近最坏情况。
使用排序前打乱的方法，仍然可能遇到n^2的行为，取决于你的分区方案。

See McIlroy's "A Killer Adversary for Quicksort"，可以去看看这个论文。
Java的快速排序实际上是非随机性的，其有一个整数数组，如果你输入它，可能会导致程序崩溃，因为递归深度过深。

目前快排最好的划分方案之一时Tony Hoare提出的方案：使用两个指针相向而行、原地操作。

## 排序本质
排序VS搜索
- 排序：对item排序。
- 搜索：检索感兴趣的数据。
很多排序算法在最坏情况下需要nlogn时间。
能否找到一个时间复杂度齐平？或者更快一点（N）？
假设TUCS，即终极基于比较排序就是那个算法，具有渐进最优的最坏情况运行时间。

TUCS 的粗略界 N ~ N log N，随后将用信息论方法证明：  
**任何基于比较的排序算法，最坏情况必须做 Ω(N log N) 次比较**，因此 TUCS 的下界也锁定在 Θ(N log N)。
- 由于TUCS是渐进最优的，R(N)同时满足：
    - R(N) ∈ O(N log N)（从上界）。
    - R(N) ∈ Ω(N)（从必须访问每个元素）。
- 但实际上，由于Ω(N log N)是更紧的下界，我们有R(N) ∈ Θ(N log N)。
因此，TUCS的理论下确界，即**TUCS的最坏情况运行时间R(N)是Θ(N log N)**。这意味着对于大规模输入，R(N)与N log N成正比，这是基于比较排序算法可能达到的最佳性能。

**无论你多么聪明，你的排序算法在最坏情况下的运行时间至少是nlogn**

## Huffman Coding（哈夫曼编码）
香农范诺采用的是自顶向下，哈夫曼采用的是自底向上。
步骤：
- 计算相对频率。  
- 将每个符号分配给一个节点，其权重等于该符号的相对频率。  
- 选取权重最小的两个节点，合并成一个超级节点，其权重为这两个节点权重之和。  
- 重复上述过程，直到所有节点合并成一棵树。

### Huffman Coding in Practice
使用霍夫曼压缩的两种可能思路：
1. **静态预训练码**：对每种输入类型（英文文本、中文文本、图像、Java 源代码等），收集该类别的海量样本输入。用这些语料分别训练出一套“标准码”——英文标准码、中文标准码等。
2. **自适应编码**：对每一个具体的输入文件，都单独生成一套只适用于该文件的编码；把这套编码随同压缩后的文件一起发送。
两种思路各自的优缺点是什么？哪一种更好？
- 方法1会导致编码效果不佳。无法达到每个符号理论的最小bit数，因为我们的编码方式没有完全匹配输入进行优化。
- 方法2要求位编码表使用额外的空间。需要将编码放入压缩的bit流，有额外开销。不过对于**非常大的输入文件**，这部分额外开销所占比例会**变得微不足道**。

给定待压缩文件 X.txt，目标生成压缩文件 `X.huf`：
1. 把 X.txt 按 b 位符号切分（例如 8 位字节、Unicode 字符等），统计这 2^b 种符号出现的次数，其中 b 为每个符号的位数。
2. 用霍夫曼编码算法构造解码 trie（字典树）和编码映射表，并将该 `trie` 存放在 `X.huf` 的开头。
3. 利用编码映射表，把输入文件中每个符号对应的码字依次写入` X.huf`。

![[Pasted image 20251123195624.png]]
解压缩 `X.huf` 时：
1. 先读入解码 `trie`。
2. 反复调用 `trie` 的 `longestPrefixOf` 操作，把 `X.huf` 中的比特流逐段还原成原始符号，直到所有比特处理完毕。
### 压缩理论
Run-length encoding，游程编码--使用字符本身加上它出现的次数来替换每个字符。
	如，原始字符串 `"AAAABBBCCDAA"` → 编码为 `('A',4)('B',3)('C',2)('D',1)('A',2)`。
LZW，这个方法有很多变体，在输入中寻找常见的重复模式。
	**原理**：在输入数据中动态构建一个字典（短语表），将重复出现的字符串替换为字典中的索引。
	如，对文本 `"ABABABA"` 会构建出 `"AB"`, `"BA"` 等短语，后续出现时用短索引代替。
需要注意的是，没有冗余的序列实际上可能会扩大，你的压缩算法可能会让情况变得更糟
### 是否可以一直重复压缩
 假设有位算法设计者声称其“SuperZip”算法能把**任意比特流**都压缩 50 %。  为什么这事根本办不到？
![[Pasted image 20251123200757.png]]
因为你需要维护编码和解码的过程。
- 每次压缩都会减少数据中的 **冗余**，使数据变得更 **随机**（熵增加）。
- 当数据达到 **信息熵** 下界时（即每个比特几乎都是独立的、等概率的 0/1），任何无损压缩算法都无法再缩小它——因为再缩小就会违反鸽巢原理。

通用压缩时不可能存在的，**比较不同的压缩算法**仍然可能非常棘手。
要考虑压缩算法本身在空间上的实际成本。
把解压过程当成一个整体模型来看，我们可以把**压缩算法**和**压缩后的比特流**合并成**一条连续的比特序列**。
- 可以把“算法 + 压缩数据”看成一段输入，交给某种**解释器**去执行（类似 CS61A 里讲的）。  
- 再往下追到底层，这些抽象最终都会落到**某种物理机器**上（参见 CS61C）。
即自解压，**压缩+解压的整个流程，可以压缩成“一段比特+一台能执行它的机器”**

### 最佳的压缩方式
对于给定的bit流，最佳的压缩方式是什么？

问题 1：可理解的压缩  
能否做出一种“可理解”的压缩——给定目标比特流 B，输出**有用且可读**的 Java 代码？
问题 2：最优压缩  
能否做出一种最优压缩——给定目标比特流 B，输出**最短可能的 Java 程序**，该程序运行后恰好生成 B？
![[Pasted image 20251123204354.png]]

在复杂性理论中，有一个概念叫 Kolmogorov Complexity ，它与最优压缩目标紧密相连。
事实：
1. Kolmogorov复杂度**与编程语言几乎无关**，
你选任何语言Kolmogorov复杂度都在常数因子范围内都是相同的，因为每个解释器的大小都只是一个常数因子。
2. 根本写不出一个程序，能**算出任意比特流的Kolmogorov复杂度**。
既然连“最短程序有多长”都算不出来，那当然更不可能**真正找到那个最短程序**。

可不可以得到一个最优的压缩算法？
理论上不可能，希望找到的最优压缩算法并不存在，是一个逻辑谬误。
#### 空间有界压缩（算法）
需要三个输入，一个目标bit流b，一个大小s，以及一个执行的最大字节码行数T，
它会返回一个长度小于等于s的程序，像之前一样输出b，
新的约束是，他必须在少于t行字节码执行的情况下完成。
![[Pasted image 20251124220031.png]]
基本思路：对于每个长度为s或者更短的程序，尝试编译这个程序，如果成功了（大多数并不会，因为它们只是随机的乱码字符），对于那些成功编译的，将运行该程序直到p停止，输出b；或者运行到t行字节码，意味着我们走的太远了。
我们从短程序开始，逐步到更长的程序，第一个输出b的程序就是我们想要的。
### 一个简短的或压缩的bit流是否是一个可理解bit流
不一定
可压缩性是一个罕见的性质，bit流是不可压缩的。
- 在所有可能的 bit 流中，**绝大多数是随机的**（没有规律），因此无法被无损压缩。只有极少数有规律（冗余）的 bit 流才能被压缩。 
- 这由鸽巢原理保证：可压缩的比特流数量远小于所有比特流数量。
非常复杂的模式可以从简单的规则中出现的事实。
- **虽然输出看起来很复杂、随机，但它的生成规则很简单**。因此，这个输出可以被压缩——只需存储那个短程序（规则），而不是存储全部输出。
即使是极短的程序也能产生非常复杂的输出，这就是压缩的核心所在。
- 无损压缩的本质就是**寻找产生数据的短规则**（即发现数据的规律、冗余）。

## 处理复杂
好坏程序员的区分关键就是他们处理复杂性的能力  --  层次抽象化，易插拔和可插拔。
**复杂性的积累，是因为成百上千个小依赖和小模糊点随着时间的推移不断堆积。最终，这些问题如此之多，以至于每一个可能的变化都会受到其中若干个的影响。**
	`Ousterhout` 提倡一种**零容忍**的哲学--遇到复杂性的不良症状时，你就应该停下来、退后一步、重构代码，重新运行单元测试，然后带着你新的、更美的设计前进。

对于每一个新的类或任务：
不要直接实现第一个想到的点子，而是先尝试想出（甚至部分实现）几种不同的方案。  
当你觉得某个方案看起来比较清晰、优雅时，再完整地实现它。  
在真实系统中：
要试着想象未来可能需要做出的改动，并确保你的设计能够应对这些变化。

复杂性三个特征：
- 变更放大：做一个小改动，需要改动的地方太多了。
- 认知负荷：指的是你为了更改你的代码，你需要了解多少内容。
- 未知的不确定性：指的是你不知道你的代码会影响到整个大型代码库中的哪一行代码。

下面是复杂性体现的形式：
- 难以理解代码原理。
- 进行小改进所需要的时间。例，2048从4x4到5x5的改进。
- 弄清如何实现改进。
- 一个错误的改进会引入另一个错误。

复杂性的成本：
- 在复杂系统，进行小改进需要大量的努力成本。
- 在简单系统，进行大改进所需要的努力较少。
复杂性也取决于系统中某部分被修改的频率。

**管理复杂性的思路：**
分层抽象（Hierarchical abstraction）  
- 创建分层的抽象结构，设立清晰的抽象边界！
“为变化而设计”  
- 围绕对象来组织程序。
- 让对象决定如何完成任务  
- 隐藏他人不需要的信息。

使用工具来管理复杂性
- IntelliJ提供导航功能--函数声明在哪里这个文件在哪里。debugger帮你发现错误
- JUnit测试通过增强对基础组件的信心来帮助你。
- 可视化工具则帮助你直观发现问题所在。

### 模块化设计：
构建程序时，最重要的事情之一就是隐藏复杂性。
在理想情况下，系统应被拆分成若干模块，每个模块都完全独立。这里的“模块”是泛指：可以是一个类、一个包，或任何代码单元。
现实中模块不可能彻底独立，因为代码总要调用别的模块，**模块化设计的目标是把模块间的依赖降到最低**。

最好的模块是那些接口比其实现简单的模块。
通过拥有一个非常简单的接口，它只会给你有限的几种方式来使用模块。
Java 接口包含两部分：
- **正式部分**：方法签名列表。  
- **非正式部分**：编译器无法强制、但必须遵守的使用约定。
**正式 = 编译器可强制；非正式 = 只能靠注释、惯例、程序员自律。**
示例：
- 迭代器要求先调用 `hasNext` 再调用 `next`，否则行为异常——这是接口的**非正式**约定。
- `add` 方法遇到 `null` 输入就抛异常——也是**非正式**规则。
- 某个方法的具体运行时间，例如 `ArrayList.add` 的均摊 O(1)——同样属于**非正式**说明，只能用注释描述。

深层模块指的是：最好的模块是那些提供强大功能，但接口简单的模块。
是模块变得深入的一种方式是尽可能多地隐藏模块内部的细节。意味着将你所做的知识和设计决策嵌入到模块本身中，而不向外界透露这些细节。
信息泄露：当同一个设计决策反映在多个模块中，导致对其中一个模块的任何更改都需要对所有模块进行更改时，这种情况就会发生。
	最大原因时时间分解--构建一个系统时，主要以事件发生的顺序为设计的主要驱动力。

### 团队合作
集体智慧与以下三件事相关：
1. 小组成员的**平均社会敏感度**（通过“眼神读心”测试衡量——这个结果非常有趣）。
