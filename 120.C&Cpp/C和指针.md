## 存储类型
变量的存储类型指的是存储变量值的内存类型--普通内存、运行时栈堆、硬件寄存器。
变量的存储类型决定变量何时创建、何时销毁以及其值将保存多久。

变量的默认存储类型取决于它的声明位置。
1. 凡是在任何代码块之外声明的变量总是存储于静态内存中，也就是不属于堆栈的内存，这类变量称为静态（static）变量。对于这类变量，你**无法为它们指定其他存储类型**。静态变量**在程序运行之前创建**，在程序的整个执行期间始终存在。它始终保持原先的值，除非给它赋一个不同的值或者程序结束。
2. 在代码块内部声明的变量的缺省存储类型是自动的（automatic），也就是说它存储于堆栈中，称为自动（auto）变量。有一个关键字 auto 就是用于修饰这种存储类型的，但它极少使用，因为代码块中的变量在缺省情况下就是自动变量。在程序执行到声明自动变量的代码块时，自动变量才被创建，当程序的执行流离开该代码块时，这些自动变量便自行销毁。如果该代码块被数次执行，例如一个函数被反复调用，这些自动变量每次都将重新创建。在代码块再次执行时，这些自动变量在堆栈中所占据的内存位置有可能和原先的位置相同，也可能不同。即使它们所占据的位置相同，你也不能保证这块内存同时不会有其他的用途
3. 对于在代码块内部声明的变量，如果给它加上关键字 static，可以使它的存储类型从自动变为静态。具有静态存储类型的变量在整个程序执行过程中一直存在，而不仅仅在声明它的代码块的执行时存在。注意，修改变量的存储类型并不表示修改该变量的作用域，它仍然只能在该代码块内部按名字访问。函数的形式参数不能声明为静态，因为实参总是在堆栈中传递给函数，用于支持递归。
4. 关键字 **register 可以用于自动变量的声明**，提示它们应该存储于机器的硬件寄存器而不是内存中，这类变量称为寄存器变量。通常，寄存器变量比存储于内存的变量访问起来效率更高。但是，如果有太多的变量被声明为 register，它只选取前几个实际存储于寄存器中，其余的就按普通自动变量处理。
寄存器变量的创建和销毁时间和自动变量相同，但它需要一些额外的工作。在一个使用寄存器变量的函数返回之前，这些寄存器先前存储的值必须恢复，确保调用者的寄存器变量未被破坏。许多机器使用运行时堆栈来完成这个任务。当函数开始执行时，它把需要使用的所有寄存器的内容都保存到堆栈中，当函数返回时，这些值再复制回寄存器中。

在许多机器的硬件实现中，并不为寄存器指定地址。同样，由于寄存器值的保存和恢复，某个特定的寄存器在不同的时刻所保存的值不一定相同。基于这些理由，机器并不向你提供寄存器变量的地址。

**自动变量和静态变量的初始化存在一个重要的差别**：
- 在静态变量的初始化中，我们可以把可执行程序文件想要初始化的值放在当程序执行时变量将会使用的位置。
	完成这个任务并不需要额外的时间，也不需要额外的指令，变量将会得到正确的值。如果不显式地指定其初始值，静态变量将初始化为 0。
- 自动变量的初始化需要更多的开销，因为当程序链接时还无法判断自动变量的存储位置。事实上，函数的局部变量在函数的每次调用中可能占据不同的位置。基于这个理由，自动变量没有缺省的初始值，而显式的初始化将在代码块的起始处插入一条隐式的赋值语句。
	这个技巧造成 4 种后果：
	1. 自动变量的初始化较之赋值语句效率并无提高。除了声明为 const 的变量之外，在声明变量的同时进行初始化和先声明后赋值只有风格之差，并无效率之别。
	2. 这条隐式的赋值语句使自动变量在程序执行到它们所声明的函数（或代码块）时，每次都将重新初始化。
	3. 这点是个优点，由于初始化在运行时执行，你可以用任何表达式作为初始化值。
	4. 除非你对自动变量进行显式的初始化，否则当自动变量创建时，它们的值总是垃圾。

## static关键字
对上面做个static领域的小结：
- 当它用于函数定义时，或用于代码块之外的变量声明时，static 关键字用于修改标识符的链接属性，从 external 改为 internal，但标识符的存储类型和作用域不受影响。用这种方式声明的函数或变量只能在声明它们的源文件中访问。

## 表达式求值
隐式转换--整型提升：表达式中的字符型和短整型操作数在使用前会被转换为普通整形

算数转换“：
如果某个操作符的各个操作数属于不同的类型，那么除非其中一个操作数转换为另外一个操作数的类型，否则操作就无法进行。下面的层次体系称为寻常算术转换（usual arithmetic conversion）。
```
long double  
double  
float  
unsigned long int  
long int  
unsigned int  
int
```
int最低，long double最高。
如果某个操作数的类型在上面这个列表中排名较低，那么它首先将转换为另外一个操作数的类型，然后执行操作。
```C
int a=5000,b=25;
long c = a*b;
long c = (long)a*b
```
上面第二个计算时如果在16位而非32位的机器上计算时会产生溢出，解决方法是第三行把其中一个或全部操作数转换为long。

复杂表达式的求值顺序是由 **3 个因素** 决定的：操作符的优先级、操作符的结合性以及操作符是否控制执行的顺序。
两个相邻的操作符哪个先执行取决于它们的**优先级**，如果两者的优先级相同，那么它们的执行顺序由它们的**结合性**决定。
	结合性就是一串操作符是从左向右依次执行还是从右向左逐个执行。
	有 4 个操作符，它们可以对整个表达式的求值顺序施加控制，它们或者保证某个子表达式能够在另一个子表达式的所有求值过程完成之前进行求值，或者可能使某个表达式被完全跳过不再求值。
	1. `&&` 逻辑与
    2. `||` 逻辑或
    3. `?:` 条件（三目）运算符
    4. `,` 逗号运算符
记住，**左值**意味着一个**位置**，而**右值**意味着一个**值**。所以，**在使用右值的地方也可以使用左值，但是在需要左值的地方不能使用右值。**

- **避免在表达式里混合使用具有“副作用”的操作符**：`++`, `--`, 赋值`=`等会改变变量本身。`c + --c` 的结果是未定义的。
- **避免依赖函数参数的求值顺序**(类比着多线程的并发问题)
- **不要在一个表达式中对同一变量修改超过一次**。

## 内存和地址
计算机的内存由数以亿计的位组成，每个位可以容纳0或者1.
为了存储更大的值，把两个或者多个字节组合在一起成为更大的内存单位。
许多机器以字为单位存储整数。“字”（**word**）就是 **CPU 一次天然就能处理的固定长度的二进制块**，也就是**机器字长**。
一个字包含多个字节，但它仍只有一个地址。至于它的地址是它左边的那个字节位置，还是右边那个字节的位置，不同的机器有不同的规定。
在要求**边界对齐**（一个硬件事件）的机器傻瓜，整型值存储的起始位置只能是某些特定的字节（通常是2或者4的倍数）。但这些是硬件设计者的事情，C程序员只关注：
1. 内存中每个位置由一个独一无二的地址标识。
2. 内存中每个位置都包含一个值。
注意：
	**名称与内存位置之间的关联并不是硬件所提供的，它是由编译器为我们实现的**，硬件仍然通过地址访问内存位置。
## 值和类型
变量包好了一序列内容为0或者1的位，它们可以被解释为整数、也可以是浮点数，这取决于它们被使用的方式。
即，**不能简单地通过检查一个值的位来判断它的类型**。

## 间接访问操作符

正常情况下，无法得知编译器为每个变量所选择的存储位置，因此我们事先无法预测它们的地址
指针变量就是一个数字。

- 对未初始化或非法指针进行间接访问操作是 一般保护性异常 的根源之一。
- 对于那些要求整数必须存储于特定边界的机器而言，如果这种类型的数据在内存中的存储地址处在错误的边界上，那么对这个地址进行访问时将会产生一个错误。这种错误在 UNIX 系统中被称为“总线错误（bus error）”。
- 如果那个位置刚好有合法地址,那么那个位置的值将会被修改

## 指针的指针
一个指向指针的指针, `**c`相当于 `*(*c)`
```C
int a = 10;
int *b = &a;
int **c = &b;
```
对指针的复杂操作,左值和右值不一定都产生了变化.
详细操作看书吧, 大概理解了但是要多刷几遍.
指针算数运算限于两种方式 :
- 指针 +/- 整数, 作用效果类似于遍历
- 指针 - 指针, 只有两个指针都指向同一个数组中的元素时,才允许一个指针减去另一个指针. 结果是两个指针之间的距离
**警告 :**
```C
int value = 42;      // 一个普通的整型变量（标量变量）
int *p = &value;     // p 指向 value
int *q = p + 5;      // 对 p 进行指针运算
```
- **语法上**：编译器看到 `p` 是 `int*` 类型，`5` 是整数，`p + 5` 这个指针运算完全符合语法规则。**它会顺利编译，不会有任何错误或警告。**
- **语义上**：编译器**完全不知道** `q` 现在指向哪里。它不知道 `value` 变量在内存中“后面”跟着什么。那个地址可能属于其他变量、函数栈的一部分、甚至是不可访问的内存。编译器**不会、也无法**检查这个结果指针 `q` 是否“有意义”。
**这就是警告的核心**：编译器只检查**语法**（类型对不对，运算符能不能用），绝不检查**语义**（算出来的地址是不是你想访问的、是否安全）。

指针关系运算 :可以对两个指针值进行比较, 前提是指向同一数组, 标准未规定比较结果会产生什么后果
	“同一数组内”比的是谁先谁后；跨数组只能比“相等/不相等”，其它比较属于未定义行为。

## 可变参数列表
C 语言提供了标准库 `<stdarg.h>`，其中包含三个宏和一个类型，用于实现可变参数：
- **类型：** `va_list`
- **三个宏：**
    1. `va_start`：初始化参数列表。
    2. `va_arg`：获取下一个参数的值。
    3. `va_end`：清理参数列表。

可变参数虽然灵活，但有严格限制：
1. **参数必须按顺序访问**，不能跳着访问。
2. **必须至少有一个命名参数**，否则无法定位可变参数的开始位置。
3. **无法自动检测参数数量和类型**，必须通过其他方式告知（如 `n_values` 或 `printf` 中的格式字符串）。
4. **类型提升问题**：`char`，`short`会被提升为 `int`，`float` 会被提升为 `double`，所以在 `va_arg` 中应使用提升后的类型。

## 一维数组
数组名的值是一个指针常量，也就是数组中第一个元素的地址。
这个指针常量的类型取决于数组的类型。
只有在两种场合下，数组名并不用指针常量来表示
- 当数组名作为 **`sizeof` 操作符** 或 **单目操作符 & 的操作数** 时。sizeof 返回整个数组的长度，而不是指向数组的指针的长度。
数组和指针并非是相同--数组具有确定数量的元素，而指针只是一个标量值。编译器用数组名来记住这些属性。只有当数组名在表达式中使用时，编译器才会为它产生一个指针常量。
不能使用赋值语句吧一个数组的所有元素复制到另一个数组，必须使用一个循环一次复制一个元素。

除了算数符优先级外，数组下标引用和间接访问完全相同。
编译器不坚持数组下标，因为很难知道下标引用的是何类型指针，开销也大（检测是不是数组的元素、还需要反映自动和动态分配的数组）。
假设使用下标和间接访问都是正确的，**下标绝不会比指针更有效率，指针有时会比下标更有效率**。
```C
// 版本1：下标
for (int i = 0; i < n; i++) {
    arr[i] = 0;
}
// 版本2：指针
int *p;
for (p = arr; p < arr + n; p++) {
    *p = 0;
}
```
指针比下标更有效率的场合：
	每次计算 `array[a]` 时，编译器必须生成指令来计算 `a * sizeof(int)`（这里是 4）。这个乘法在**运行时**执行，消耗时间和空间。
移位操作比乘法操作要快。
1. 当你根据某个固定数目的增量在一个数组中移动时，使用指针变量将比使用下标产生效率更高的代码。当这个增量是 1 并且机器具有地址自动增量模型时，这点表现得更为突出。
2. 声明为寄存器变量的指针通常比位于静态内存和堆栈中的指针效率更高（具体提高的幅度取决于你所使用的机器）。
3. 如果你可以通过测试一些已经初始化并经过调整的内容来判断循环是否应该终止，那么你就不需要使用一个单独的计数器。
4. 那些必须在运行时求值的表达式较之诸如 `&array[SIZE]` 或 `array+SIZE` 这样的常量表达式往往代价更高。
代码速度优化建议：关键是你要先确认程序中那些代码占用了绝大部分运行时间，然后再把你的精力集中在这些代码上改进它们。

指针和数组并不是相等的：
- 声明一个数组时，编译器将根据声明所指定的元素数量为数组保留内存空间，然后再创建数组名，它的值是个常量，指向这段空间的起始位置。
- 声明一个指针变量时，编译器只为指针本身保留内存空间，它并不为任何整型值分配内存空间。而且，指针变量并未被初始化为指向任何现有的内存空间，如果它是一个自动变量，它甚至根本不会被初始化。

---
对于一个并不打算修改这些字符的函数而言，预先把它声明为常量有何重要意义呢？
1. 这是一种良好的文档习惯。有些人希望仅观察该函数的原型就能发现该数据不会被修改，而不必阅读完整的函数定义。
2. 编译器可以捕捉到任何试图修改该数据的意外错误。
3. 这类声明允许向函数传递 const 参数。
在许多机器上，register 变量（**手动分配寄存器**）所产生的代码将比静态内存中的变量和堆栈中的变量所产生的代码执行速度更快。
	取决于在你的环境中，使用 register 变量是否能够产生更快的代码。许多当前的编译器比程序员更加懂得怎样合理分配寄存器。对于这类编译器，在程序中使用 register 声明反而可能降低效率。
这个相等性暗示指针和数组名实际上是相等的但只是在当前这个上下文环境中。
```C
int strlen(char *string);  
int strlen(char string[]);
```
指针的这种表述事实上是更精确的。

如果你在函数内声明一个大数组，并且：
- **需要每次进入函数都重新初始化** → 用普通局部数组
- **不需要每次都重新初始化**（或初始化成本太高）→ 考虑用 `static` 数组
字符数组的两种初始化方式：
1. **用于初始化字符数组时** → **初始化列表**
```C
char message[] = { 'H', 'e', 'l', 'l', 'o', 0 }; //不要用这个
char message[] = "Hello";  // 这是初始化列表的简写
```
适用于**可修改的字符串**
2. **用于赋值给指针时** → **字符串常量**
```C
char *message2 = "Hello";  // 这是字符串常量
```
适用于**只读的字符串引用**

- 利用部分初始化特性，避免冗长的列表。
- 编译器通常能更好地检查嵌套花括号中的维度匹配错误。
## 指针数组
**两种存储字符串集合的方式**
1. **方式A：指针数组（更灵活）**
```C
const char *keyword[] = {
    "do", "for", "if", "register", "return", "switch", "while"
};
```
- **内存布局**：每个指针指向独立的字符串常量
- **优点**：
    - 各字符串长度可以不同，没有空间浪费
    - 添加NULL结尾可以方便遍历（无需知道长度）
- **缺点**：需要额外存储指针本身
2. **方式B：二维字符数组/矩阵（更紧凑）**
```c
const char keyword[][9] = {  // 9 = 最长字符串"register"长度(8) + 1
    "do", "for", "if", "register", "return", "switch", "while"
};
```
- **内存布局**：连续内存块，每行固定长度（9字节）
- **优点**：
    - 不需要指针，整体可能更紧凑（如果字符串长度相近）
    - 数据局部性好
- **缺点**：
    - 短字符串浪费空间（用`\0`填充）
    - 必须按最长字符串设定列宽
---
** 如何选择？**
- **字符串长度差异大** → 用**指针数组**（节省空间）
- **字符串长度相近** → 用**二维数组**（避免指针开销）
- **现代系统**：通常差异不大，指针数组更常用（灵活性高）
# ch09-字符串、字符和字节
C语言没有显式的字符串数据类型，因为字符串以字符串常量的形式出现或者存储在字符数组种。
`strlen`返回一个类型为`size_t`的值，一个无符号整数类型。

---
最常用的字符串函数都是“不受限制”的 -- 它们通过寻找字符串参数结尾的 NUL 字节来判断它的长度。这些函数一般都指定一块内存用于存放结果字符串。在使用这些函数时，程序员必须保证结果字符串不会溢出这块内存。

字符串比较的原理：
**逐字符比较**：从两个字符串的第一个字符开始，按 ASCII 值逐个比较。
比较规则：
    1. 遇到第一个不同的字符时，比较这两个字符的 ASCII 值。
    2. ASCII 值较小的字符所在的字符串被认为是“较小”的。
    3. 如果一个字符串是另一个字符串的前缀（例如 `"abc"` 和 `"abcd"`），则较短的字符串被认为“较小”（因为 `\0` 出现更早）。
这种比较方式称为**词典比较**（lexicographic comparison）。
三个重要警告（常见错误）：
-  不要直接用返回值作为布尔条件
-  返回值不一定是 1 或 -1
-  确保字符串以 `\0` 结尾
---
长度受限的字符串函数：
和不受限版本一样，如果原参数和目标参数发生重叠，那么它们就是违背定义的。

注意：** `strncpy` 的结果不是以NUL字节结尾的**。
这个问题只有当你使用 `strncpy` 函数创建字符串，然后或者对它们使用 str 开头的库函数，或者在 `printf` 中使用 %s 格式码打印它们时才会发生。

---
**错误信息：**
当你调用一些函数，请求操作系统执行一些功能如打开文件时，如果出现错误，操作系统是通过设置一个外部的整型变量 `errno` 进行错误代码报告的。`strerror` 函数把其中一个错误代码作为参数并返回一个指向用于描述错误的字符串的指针。这个函数的原型如下：
```C
char *strerror(int error_number);
```
事实上，返回值应该被声明为 const，因为你不应该修改它。

直接测试或者操作字符将会降低程序的可移植性。

**内存操作**：
 C 语言中**处理任意内存（字节序列）的函数**，通常称为“内存操作函数”或“字节操作函数”。这些函数与字符串函数不同，它们**不依赖 NUL 结尾**，可以处理包含零值（`\0`）的任意数据（如结构体、整数数组等）。

- 内存操作函数**显式指定长度**（`length` 参数），可以操作任意字节序列，无论其中是否有零值。

# ch10-结构和联合
## 结构基础
聚合数据类型能够同时存储超过一个的单独数据。
C提供了两种类型的聚合数据类型 -- 数组和结构。
数组是相同类型的元素集合，它的每一个元素是通过下标引用或者指针间接访问来选择的。
- 数组元素可以通过下标访问，这只是因为数组的元素长度相同。
- 在结构中情况并非如此。由于一个结构的成员可能长度不同，所以不能使用下标来访问它们。相反，每个结构成员都有自己的名字，它们是通过名字访问的。
结构变量属于标量类型，所以你可以像对待其他标量类型那样执行相同类型的操作。

```c
struct tag{
	member-list;
} variable-list;
```
tag字段允许为成员列表提供一个名字，这样它就可以在后续的声明中使用。
如果你想在多个源文件中使用同一种类型的结构，你应该把标签声明或 typedef 形式的声明放在一个头文件中。当源文件需要这个声明时可以使用 `#include` 指令把那个头文件包含进来。
结构成员的间接访问：
箭头运算符 `->` 把‘先解指针再取成员’两步合成一步写：`p->member` 等价于 `(*p).member`。

---
**结构的自引用：**
```C
struct SRL_MP3 {
	struct SRL_MP3 b; // 错误：成员b是完整结构体，引发无限嵌套
    struct SRL_MP3 *b; // 正确：b是指针，指向同类型不同结构体
    int g;
    int h;
};
```
**合法情况**：结构体包含指向自身的指针（如 `struct SRL_MP3 *b;`），因为指针大小固定（如4或8字节），编译器在结构体定义完成前就能确定指针大小，因此是合法的。

**typedef中的自引用陷阱**
**错误示例**：在typedef结构体时，直接在内部使用尚未定义的typedef类型名进行自引用，会导致编译错误，因为类型名在结构体内部还未生效。
```C
typedef struct {
    int a;
    SELF_REF3 *b; // 错误：SELF_REF3在此处未定义
    int c;
} SELF_REF3;
```
**解决方案**：使用结构体标签（struct tag）先声明结构体类型，内部通过标签定义指针，最后用typedef创建别名。这样标签在结构体内部是可见的。
```C
typedef struct SELF_REF3_TAG { // 先定义结构体标签
    int a;
    struct SELF_REF3_TAG *b; // 正确：使用标签声明指针
    int c;
} SELF_REF3; // 最后创建类型别名
```
关键：
- 结构体自引用必须通过指针实现，避免无限大小问题。
- typedef定义自引用结构体时，需借助结构体标签来“向前声明”，确保编译器能识别类型。
--- 
**嵌套结构：**
问题的本质：循环依赖
- 当两个结构体需要互相包含对方时（例如A包含B的指针，B包含A的指针），会出现**声明顺序的困境**：无论先声明哪一个，另一个都尚未定义。
- 和自引用类似，必须使用**指针**形式，直接包含完整结构体会导致无限嵌套。
**解决方案：前向声明（不完整声明）**
- 先使用**不完整声明**（只声明结构体标签，不定义成员），让编译器知道该标签代表一个结构体类型。
- 不完整声明后，就可以在另一个结构体中声明**指向该结构体的指针**（因为指针大小固定，无需知道结构体完整定义）
```C
struct B; // 步骤1：前向声明B（不完整声明）
struct A { // 步骤2：定义A
    struct B *partner; // 合法：B的标签已声明
    // 其他成员
};
struct B { // 步骤3：定义B
    struct A *partner; // 合法：A已完全定义
    // 其他成员
};
```

1. 内存排布  ：

2. 减小浪费的方法  ：
把对齐要求最严格的成员放前面，最宽松的放后面，可最大限度压缩填充。  
若为了可读性/维护性想把相关字段放一起，也可保留顺序，但要在注释里说明；当结构实例数量巨大时，优先节省空间。

## 作为函数参数的结构
结构变量是一个标量，可出现在标量出现的任何场景。因而将结构作为参数传递给一个函数是合法的，但这种做法不适应。
这个方法能够产生正确的结果，但它的效率很低，因为 C 语言的参数传值调用方式要求把参数的一份拷贝传递给函数。
- 即，**不要传递给函数一个 结构 作为参数，而要传递一个指向结构的指针**。
结构越大，传递指针的效率越高。
在许多机器中，你可以把参数声明为寄存器变量，从而进一步提高指针传递方案的效率。在有些机器上，这种声明在函数的起始部分还需要一条额外的指令，用于把堆栈中的参数（参数先传递给堆栈）复制到寄存器，供函数使用。但是，如果函数对这个指针的间接访问次数超过两三次，那么使用这种方法所节省的时间将远远高于一条额外指令所花费的时间。
注意：
	传递意味着你可以对调用程序的结构变量进行修改。

## 位段
**位段**是结构体的一种特殊形式，允许成员按**位（bit）** 而非字节为单位存储。
- **位段成员类型**必须是 `int`、`signed int` 或 `unsigned int`（推荐显式指定符号性）。
- 声明方式：在结构体成员后加冒号和位数，如 `unsigned ch : 7;` 表示`ch`占用7个比特位。
**位段的主要用途**：
- **节省存储空间**：将多个短位段（**长度可以是奇数**）打包在一个整型变量中，避免空间浪费。
- **方便访问硬件寄存器**：在系统编程（如操作系统、嵌入式系统）中，硬件寄存器常将多个控制/状态位打包在一个整型值中。
第二条解释：
	很方便地访问一个整型值的部分内容。它可能出现于操作系统中。
	例如：用于操作软盘的代码必须与磁盘控制器通信。这些设备控制器常常包含了几个寄存器，每个寄存器又包含了许包装在一个整型值内的不同的值。位段就是一种方便的访问这些单一值的方法。

**位段的严重缺点：可移植性差**
**实现依赖性强**，不同编译器/平台可能导致：
1. `int`位段被当作有符号还是无符号数（应显式声明）。
2. 位段的最大长度限制（可能受机器字长影响）。
3. **内存分配方向不确定**：位段在整型变量中可能是**从左向右（高位到低位）** 或**从右向左（低位到高位）** 分配。
4. **位段跨越边界的行为不确定**：当一个位段无法放入当前整型的剩余空间时，编译器可能将其放在下一个整型中，也可能直接重叠存放。

 对比：
- 位段：源代码更简洁易读。
- 手动位操作：可移植性更强，但代码更复杂。
**任何用位段实现的功能都可以用移位和屏蔽实现**（**手动位操作**）。
## 联合
联合的声明和结构类似，但它的行为方式却和结构不同。**联合**的所有成员引用的是**内存中的相同位置**。当你想在不同的时刻把不同的东西存储于同一个位置时，就可以使用联合。
 **核心特性**:
- 所有成员共享同一块内存，大小由最大成员决定
- 同一时间只能存储一个成员的值（覆盖前一个）
- 访问方式决定内存的解释方式
```C
union { 
	float f; 
	int i; 
} fi;
```
- 在32位机器上，`fi` 占用4个字节
- `fi.f = 3.14159;` → 存储浮点数
- `printf("%d\n", fi.i);` → 将同样的位解释为整数

**联合的主要用途**:
1. 类型双关（Type Punning）: 查看同一内存的**不同解释方式**
2. **节省内存空间**:当数据在不同时刻具有不同类型时，避免为每种类型都分配独立内存
使用场景：
- **解释器中的变量存储（BASIC示例）**:多个字段只具备一个类型，在某一时刻只有一个被使用
- **变体记录（Variant Record）**：内存中某个特定区域将在不同时刻存储不同类型的值

**要点**
![[Pasted image 20260104104127.png]]
内存分配规则
- 联合的大小 = 最大成员的大小
- 如果成员长度差异很大 → 考虑存储指针而非数据本身
初始化限制
- 只能初始化第一个成员 
- 必须使用花括号
程序员的责任
- 编译器不检查类型匹配：访问错误的联合成员是未定义行为
- 必须维护标签字段：用`enum`等标识当前有效成员

联合的问题：
```C
struct PARTINFO {
    int cost;          // 4字节
    int supplier;      // 4字节
    // 总共约8字节
};
struct SUBASSYINFO {
    int n_parts;       // 4字节
    struct {
        char partno[10];  // 10字节
        short quan;       // 2字节
    } parts[MAXPARTS];    // 假设MAXPARTS=100 → 1200字节
    // 总共约1204字节
};
struct INVREC {
    char partno[10];   // 10字节
    int quan;          // 4字节
    enum { PART, SUBASSY } type;  // 4字节
    union {
        struct PARTINFO part;      // 8字节
        struct SUBASSYINFO subassy; // 1204字节 ← 最大成员
    } info;  // 联合大小 = 1204字节
};
// 整个INVREC大小 ≈ 10+4+4+1204 = 1222字节
```
即使存储的是**小零件**（只需要8字节的`part`），联合仍然分配**1204字节**（因为`subassy`最大）
**使用指针的解决方案**:
```C
struct INVREC {
    char partno[10];
    int quan;
    enum { PART, SUBASSY } type;
    union {
        struct PARTINFO *part;      // 指针：8字节
        struct SUBASSYINFO *subassy; // 指针：8字节
    } info;  // 联合大小 = 8字节（两个指针大小相同）
};
// 整个INVREC大小 ≈ 10+4+4+8 = 26字节
```
内在逻辑：
```C
// 存储零件时：
struct INVREC rec;
rec.type = PART;
rec.info.part = malloc(sizeof(struct PARTINFO));  // 只分配8字节
// 存储装配件时：
rec.type = SUBASSY;
rec.info.subassy = malloc(sizeof(struct SUBASSYINFO));  // 按需分配1204字节
```
# ch11-动态内存分配
因为数组所需地内存空间取决于输入的数据，因此数组的长度常常在运行时才知道，而声明时必须指定常量指定数组长度。
- 当一个程序需要一些内存时，就调用 malloc函数
参数是需要分配的字节数，从内存池中提取一块合适的连续内存，并返回一块指向这块内存的指针。事实上实际分配的会比请求的略多一些。
如果内存池剩余有限无法满足请求，该函数会向OS发送请求；OS如果无法提供更多内存，该函数就会返回一个NULL指针。
```text
malloc又是如何知道你所请求的内存需要存储的是整数、浮点值、结构还是数组呢？它并不知情——malloc返回一个类型为 void* 的指针，正是缘于这个原因。标准表示一个 void* 类型的指针可以转换为其他任何类型的指针。但是，有些编译器，尤其是那些老式的编译器，可能要求你在转换时使用强制类型转换。

对于要求边界对齐的机器，malloc 所返回的内存的起始位置将始终能够满足对边界对齐要求最严格的类型的要求。
```

- 当一块以前分配的内存不再使用的时候，程序调用 free函数
该函数的**参数**要么是**NULL**（传一个NULL值并不会产生任何效果），要么是以前**从malloc、calloc或realloc返回的值** -- 一个指针。
释放一块内存的一部分是不被允许的，动态分配的内存必须一起释放。

- calloc函数，也用于分配内存
相较于malloc。它会在返回指向内存的指针之前把它初始化为0，
且其参数包括所需元素数量和每个元素的字节数。
- realloc函数，用于修改一个原先已经分配的内存块的大小
如果它用于 **扩大** 一个内存块，那么这块内存原先的内容依然保留，新增加的内存添加到原先内存块的后面，新内存并未以任何方法进行初始化。
如果它用于 **缩小** 一个内存块，该内存块尾部的部分内存便被拿掉，剩余部分内存的原先内容依然保留。
如果原先的内存块 **无法改变** 大小，该函数将分配另一块正确大小的内存，并把原先那块内存的内容复制到新的块上。因此，这种情况下在**使用 `realloc` 之后，应该改用 `realloc` 所返回的新指针**。
最后，如果该函数的第 1 个参数是 NULL，那么它的行为就和 malloc 一模一样。

---
**常见的动态内存错误包括：**
- 对 NULL 指针进行解引用操作
- 对分配的内存进行操作时越过边界
- 释放并非动态分配的内存
- 试图释放一块动态分配的内存的一部分
- 一块动态内存被释放之后被继续使用
几大错误源：
1. 忘记检测所请求的内存是否成功分配。**书中有可靠检测样例**
2. 操作内存时超出了分配内存的边界
3. 访问已经被free释放的内存
被访问的内存可能保存了其它的变量的值，修改会破坏那个变量。
在malloc和free的有些实现中，它们以链表的形式维护可用的内存池。对分配的内存之外的区域进行访问可能破坏这个链表，这有可能产生异常，从而终止程序。

**悬垂指针或重复释放**：当你使用 `malloc` 分配一块内存后，可能会有**多个指针指向同一块内存**。如果其中一个指针调用了 `free()`，那么这块内存就被释放了，但**其他指针并不知道**，它们仍然指向已被释放的内存区域。
可能风险：
1. **访问已释放内存** → 未定义行为（程序崩溃、数据损坏、安全漏洞）
2. **重复释放** → 如果两个指针都尝试释放同一块内存，会导致“double free”错误，通常导致程序立即崩溃
3. **难以调试** → 问题可能不会立即显现，而是在后续某个不确定的时刻崩溃
**解决方案：**
- 指定唯一的所有者负责释放内存
- 释放后置空（这样至少可以防止同一个指针被重复使用，但无法解决其他副本指针的问题）
- 避免不必要的指针复制
- 使用工具检测

内存泄露：
当动态分配的内存不再需要使用时，它应该被释放，这样它以后可以被重新分配使用。
分配内存但在使用完毕后不释放将引起 **内存泄漏**（memory leak）。

## 函数指针
注意：对函数指针进行间接访问之前必须把它初始化为指向某个函数。
```c
int (*pf)(int) = &f;
```
声明并创建了一个函数指针pf，并把它初始化为指向函数f。
初始化表达式的 &操作符是可选的，因为函数名被使用时总是由编译器把它转换为函数指针。&只是显式地说明了编译器的隐式任务。

---
常见的两个用途是： 转换表 和 作为参数传递给另一个函数

作为参数传递给另一个函数：
```C
// 通用查找函数
Node *search_list(Node *node, void const *target,
                  int (*compare)(void const *, void const *)) {
    while(node != NULL) {
        // 关键：这里比较的是node->value指向的内容 和 target指向的内容
        if(compare(node->value, target) == 0)
            return node;
        node = node->next;
    }
    return NULL;
}
// 整数比较函数
int compare_int(void const *a, void const *b) {
    // 先把void*转换为int*，再取内容
    int int_a = *(int *)a;
    int int_b = *(int *)b;  
    if(int_a == int_b) return 0;
    return 1;
}
```
- 使查找函数与类型无关 -- 编写一个比较函数，将指向该（比较）函数的指针作为参数传递给查找函数，然后查找函数调用这个函数来执行值得比较。
- 向函数传递一个指向值的指针而不是值本身。函数有一个`void*`形参，用于接收这个参数，然后指向这个值的指针传递给函数。
**回调函数**：用户把一个函数指针作为参数传递给其它函数，后者回调用户函数。

转移表：
把具体操作和选择操作的代码分开是一种良好的设计方式。
转移表就是**用函数指针数组实现的多路分支**，比switch更简洁，但要注意数组越界检查。
```c
// 以前：每个操作符都要写case
switch(oper) {
    case ADD: result = add(op1, op2); break;
    case SUB: result = sub(op1, op2); break;
    // ... 如果有一百个操作符，要写一百行
}
```
**用数组存函数指针**
```c
// 现在：用数组代替
double (*oper_func[])(double, double) = {
    add,   // 下标0 → ADD
    sub,   // 下标1 → SUB
    mul,   // 下标2 → MUL
    div    // 下标3 → DIV
};
// 调用：直接通过下标调用
result = oper_func[oper](op1, op2);
```
**魔法揭秘**：
- `oper_func[0]` 就是 `add` 函数的地址
- `oper_func[1]` 就是 `sub` 函数的地址
- `oper_func[oper]` = 取出对应函数的地址
- `oper_func[oper](op1, op2)` = 调用这个函数

宏：
允许把参数替换到文本中，这种实现通常叫 **宏 或 定义宏**
**宏的问题：**
```C
/* 陷阱 1：优先级被悄悄改变 */
#define SQUARE_BAD(x)   x * x          /* 只替换文本，无括号保护 */
#define SQUARE_OK(x)   ((x) * (x))    /* 整体再加一层括号 */
int a = 5;
/* 调用处 */
printf("%d\n", SQUARE_BAD(a + 1));     /* 展开: a + 1 * a + 1  → 11  */
printf("%d\n", SQUARE_OK(a + 1));      /* 展开: ((a + 1) * (a + 1)) → 36  */


/* 陷阱 2：宏展开后变成“两条”表达式，再次翻车 */
#define DOUBLE_BAD(x)  (x) + (x)       /* 仅参数加括号，整体缺外套 */
#define DOUBLE_OK(x)   ((x) + (x))     /* 给整个表达式穿“外套” */
/* 调用处 */
printf("%d\n", 10 * DOUBLE_BAD(a));    /* 展开: 10 * (a) + (a)  → 55  */
printf("%d\n", 10 * DOUBLE_OK(a));     /* 展开: 10 * ((a) + (a)) → 100 */
```
宏里凡是有运算符，就套两层括号——先给整个表达式穿外套，再给每个参数穿内衣.

---
**`#define`替换**
**宏扩展的步骤**：
1. 检查宏的参数中是否有`#define`定义的符号，如果有，先替换它们。
2. 将宏的替换文本插入到程序中，并将参数名替换为参数的值（即已经替换过的参数值）。
3. 再次扫描替换后的文本，看是否包含任何`#define`定义的符号，如果有，重复上述过程（即重复1和2）。
注意：宏不可以递归。
预处理器在搜索`#define`定义的符号时，不会检查字符串常量内部。也就是说，如果宏参数出现在字符串常量中，不会被替换。
想要把宏参数插入到字符串常量中，两种方法：
- 使用字符串自动连接
```C
#define PRINT(FORMAT, VALUE) \
    printf("The value is " FORMAT "\n", VALUE)
```
- 使用`#`将宏参数转换为字符串
```C
#define PRINT(FORMAT, VALUE) \
    printf("The value of " #VALUE " is " FORMAT "\n", VALUE)
```
**使用`##`连接符号**:
`##` 将两边的符号连接成一个符号，可以用来创建新的标识符。
```C
#define ADD_TO_SUM(sum_number, value) \
    sum ## sum_number += value
```

宏与函数：
宏被频繁用于简单的计算。
为什么不用函数来完成这个任务呢？
- 用于调用和从函数返回的代码很可能比实际执行这个小型计算工作的代码更大，所以使用宏比使用函数在程序的规模和速度方面都更胜一筹
- 函数的参数必须声明为一种特定的类型，宏可以用于整型、长整型、单浮点型、双浮点数以及其他任何可执行函数的类型。换句话说，**宏是与类型无关的**
不利在于：
	使用宏时，一份宏代码都将插入到程序中。除非宏很短，否则宏将大幅度增加程序长度。

---
带副作用的宏参数
当宏参数在宏定义中出现的次数超过一次时，如果这个参数具有副作用，那么当你使用这个宏时就可能出现危险，导致不可预料的结果。
**副作用就是在表达式求值时出现的永久性效果。**
```C
x + 1
x++
```
上面作为宏定义就没有副作用，即调用多少次值都一样；下面这个缺有。
不要用宏来定义**奇偶校验**。
奇偶校验就是“数 1 的个数补一位”，让接收方快速发现“好像多了一个或少了一个 1”的简单手段。

## 条件编译
使用条件编译，可以选择代码的一部分是被正常编译还是完全忽略

所谓常量表达式，就是说它或者是字面值常量，或者是个由 `#define` 定义的符号。如果变量在执行期之前无法获得它们的值，那么它们如果出现在常量表达式中就是非法的，因为它们的值在编译时是不可预测的。

## 文件包含
`#include` 指令使另一个文件的内容被编译，就像它实际出现于 `#include` 指令出现的位置一样。
这种替换执行的方式很简单：预处理器删除这条指令，并用包含文件的内容取而代之。
这样，一个头文件如果被包含到 10 个源文件中，它实际上被编译了 10 次。
**当头文件被包含时，位于头文件内的所有内容都要被编译**。
因此，只把必要的声明包含在一个头文件中这种做法更好一些，此外这样文件就**不会意外地访问一些应该属于私有的函数或变量**。

---
编译器支持两种不同类型的 `#include` 文件包含：函数库文件和本地文件。
1. 函数库文件
```c
#include <filename>
```
对于 filename，并**不存在任何限制**，不过**根据约定**，标准库文件以一个 `.h` 后缀结尾。
2. 本地文件包含
```c
#include "filename"
```

-  **当前源文件所在目录**（这是最主要的区别！）
-  **如果没找到**，则**回退**到标准库路径查找（和`<filename>`一样）

---
嵌套
嵌套 `#include` 文件如何被识别？
**预处理器的处理流程**
预处理器（preprocessor）按顺序处理源文件，当遇到 `#include` 时：
```C
// main.c
#include "header1.h"  // 预处理器暂停处理main.c，转向header1.h

// 假设header1.h内容：
#include "common.h"
#include "utils.h"

// 预处理器会先处理common.h，然后是utils.h
// 当header1.h全部处理完后，才返回main.c继续
```
**编译器通过以下方式跟踪嵌套包含**：
- **内部堆栈机制**：编译器维护一个"包含栈"（include stack）
- **防止无限递归**：编译器会检测循环包含，标准要求至少支持8层嵌套
- **路径缓存**：现代编译器会缓存已处理头文件路径，避免重复读取

同一文件被嵌套调用时多次包含如何解决？
1. **头文件保护（Header Guards）**
```C
// config.h
#ifndef CONFIG_H      // 第1次：CONFIG_H未定义 → 进入
#define CONFIG_H      // 定义CONFIG_H宏

#define MAX_USERS 100
typedef struct User { ... } User;
#endif               // 结束

// 第2次包含时：CONFIG_H已定义 → 跳过整个文件内容
```
2. **#pragma once（非标准但广泛支持）**
```C
// config.h
#pragma once          // 告诉编译器：这个文件只包含一次

#define MAX_USERS 100
typedef struct User { ... } User;
```

它通知预处理器 number 是下一行输入的行号。如果给出了可选部分 “string”，预处理器就把它作为当前文件的名字。值得注意的是，这条指令将修改 `__LINE__` 符号的值，如果加上可选部分，它还将修改 `__FILE__` 符号的值。

`#pragma` 指令是另一种机制，用于支持因编译器而异的特性。它的语法也是因编译器而异。
有些环境可能提供一些 `#pragma` 指令，允许一些编译选项或其他任何方式无法实现的一些处理方式。
	例如，有些编译器使用 `#pragma` 指令在编译过程中打开或关闭清单显示，或者把汇编代码插入到 C 程序中。
从本质上说，`#pragma` 是不可移植的。预处理器将忽略它不认识的 `#pragma` 指令，两个**不同的编译器可能以两种不同的方式解释同一条 `#pragma` 指令**。

**无效指令**（null directive）就是一个 `#` 符号开头，但后面不跟任何内容的一行。这类指令只是被预处理器简单地删除。
```c
#
#include <stdio.h>
#
```
这个例子中的无效指令通过把 include 与周围的代码分隔开来，凸显它的存在。
也可以通过插入空行取得相同的效果。

## ANSI I/O概念
ANSI C 进一步对 I/O 的概念进行了抽象。就 C 程序而言，所有的 I/O 操作只是简单地从程序移进或移出字节的事情。
这种字节流便被称为流（stream）。程序只需要关心创建正确的输出字节数据，以及正确地解释从输入读取的字节数据。
![[Pasted image 20260105122456.png]]
只有当操作系统可以断定它们与交互设备并无联系时才会进行完全缓冲。否则，它们的缓冲状态将因编译器而异。
一个常见（但并不普遍）的策略是把标准输出和标准输入联系在一起，就是当请求输入时同时刷新输出缓冲区。
事实上，如果程序失败，缓冲输出可能不会被实际写入。

文本流：
流分为两种类型，文本（text）流和二进制（binary）流。
- 文本流的有些特性在不同的系统中可能不同。其中之一就是文本行的最大长度。标准规定至少允许 254 个字符。另一个可能不同的特性是文本行的结束方式。
- 二进制流中的字节将完全根据程序编写它们的形式写入到文件或设备中，而且完全根据它们从文件或设备读取的形式读入到程序中。

对于每个 ANSI C 程序，运行时系统提供三个自动打开的文本流：标准输入（standard input）、标准输出（standard output）和标准错误（standard error）。
	这些流的名字分别为 `stdin`、`stdout` 和 `stderr`，它们都是一个指向 FILE 结构的指针。
	标准输入是默认情况下输入的来源，标准输出是默认的输出设置。具体的默认值因编译器而异，通常标准输入为键盘设备，标准输出为终端或屏幕。
为错误信息准备一个不同的流意味着，**即使标准输出重定向到其他地方，错误信息仍将出现在屏幕或其他缺省的输出设备上**。

一个程序同时最多能够打开多少个文件呢？
	它和编译器有关，但可以保证你能够同时打开至少 FOPEN_MAX 个文件。这个常量包括了三个标准流，它的值至少是 8。
常量 FILENAME_MAX 是一个整型值，用于提示一个字符数组应该多大以便容纳编译器所支持的最长合法文件名，这个常量的值就是文件名的推荐最大长度。
## 流I/O
下面是关于文件 I/O 的一般概况。
1. 程序为必须同时处于活动状态的每个文件声明一个指针变量，其类型为 `FILE *`。这个指针指向这个 `FILE` 结构，当它处于活动状态时由流使用。
2. 流通过调用 `fopen` 函数打开。为了打开一个流，你必须指定需要访问的文件或设备以及它们的访问方式（例如，读、写或者既读又写）。`fopen` 和操作系统验证文件或设备确实存在（在有些操作系统中，还验证你是否允许执行你所指定的访问方式）并初始化 `FILE` 结构。
3. 然后，根据需要对该文件进行读取或写入。
4. 最后，调用 `fclose` 函数关闭流。关闭一个流可以防止与它相关联的文件被再次访问，保证任何存储于缓冲区的数据被正确地写到文件中，并且释放 `FILE` 结构使它可以用于另外的文件。
I/O 函数以三种基本的形式处理数据：文本行和二进制数据。每种有不同的处理方式。
![[Pasted image 20260105125850.png]]
行 I/O 可以用两种方式执行——未格式化的或格式化的，区别在于：
- 未格式化的 I/O（`unformatted line I/O`）简单读取或写入字符串
- 格式化的 I/O 则执行数字和其他变量的内部和外部表示形式之间的转换。
当格式化字符串达到末尾或者读取的输入不再匹配格式字符串所指定的类型时，输入就会停止。
`scanf` 函数家族中的 format 字符串参数可能包含下列内容：
- 空白字符——它们与输入中的零个或多个空白字符匹配，在处理过程中将被忽略。
- 格式代码——它们指定函数如何解释接下来的输入字符。
- 其他字符——当任何其他字符出现在格式字符串时，下一个输入字符必须与它匹配。如果匹配，该输入字符随后就被丢弃；如果不匹配，函数就不再读取直接返回。
`scanf` 函数家族的格式代码都以一个百分号 `%` 开头，后面可以是
1. 一个可选的星号，星号将使转换后的值被丢弃而不是进行存储
2. 一个可选的宽度，宽度以一个非负的整数给出，它限制将被读取用于转换的输入字符的个数；如果未给出宽度，函数就连续读入字符直到遇见输入中的下一个空白字符。
3. 一个可选的限定符，用于修改有些格式的代码的含义。
4. 格式代码
限定符的目的是为了指定参数长度。
这些函数都从输入源读取字符并根据 format 字符串给出的格式代码对它们进行转换。 
- `fscanf` 的输入源就是作为参数给出的流
- `scanf` 从标准输入读取
- `sscanf` 则从第 1 个参数所给出的字符串中读取字符

`printf` 函数原型中的 `format` 字符串可能包含格式代码，它使参数列表的下一个值根据指定的方式进行格式化，至于其他的字符则原样逐字打印。格式代码由一个百分号 `%` 开头，后面跟  
1. 零个或多个标志字符，用于修改有些转换的执行方式，  
2. 一个可选的最小字段宽度，  
3. 一个可选的精度，  
4. 一个可选的修改符，  
5. 转换类型。
`printf` 根据格式代码和 format 参数中的其他字符对参数列表中的值进行格式化。这个家族的另两个函数的工作过程也类似。
- 使用 `printf`，结果输出送到标准输出
- 使用 `fprintf`，你可以使用任何输出流
- `sprintf` 把它的结果作为一个 NUL 结尾的字符串存储到指定的 buffer 缓冲区而不是写入到流中
警告：
	1. `sprintf` 潜在溢出问题：缓冲区大小不是参数，输出过长会覆写后续内存；可预先计算最大可能长度或限制宽度。
	2. `printf` 族与 `scanf` 族的格式代码语法不同，不可混用。
	3. 参数类型必须与格式代码完全匹配，否则可能输出垃圾甚至崩溃，编译器无法自动检查。

**警告与注意事项**
1. 缓冲区生命周期问题
```C
// 危险示例：使用局部数组作为缓冲区
void dangerous_function() {
    char local_buffer[BUFSIZ];  // 自动变量，函数结束时失效
    setbuf(stdout, local_buffer);
    // 函数返回后，stdout仍可能使用已释放的内存！
}
```

**关键点**：确保缓冲区在流关闭前始终有效
2. 缓冲区大小选择
建议使用`BUFSIZ`（stdio.h中定义）或其整数倍 
过大缓冲区可能适得其反：
- 与操作系统内部缓冲不匹配导致额外磁盘操作
- 在MS-DOS中，缓冲区大小如果匹配磁盘簇大小可提高效率
2. 操作系统级缓冲
即使关闭C库缓冲，操作系统可能仍有缓冲.

## **信号**
信号是操作系统异步抛给程序的“突发事件”；
程序可选择默认处理（通常是终止）、忽略，或注册自己的信号处理函数来抢救数据、安全退出。

**信号名**`<signal.h>`
下图是标准定义的信号：
![[Pasted image 20260105164650.png]]
前面的信号都是同步的，最后两个SIGINT 和 SIGTERM 都是异步的。

当一个信号发生时，程序可以使用三种方式对它作出反应。
- 默认的反应是由编译器定义的，通常是终止程序
- 程序也可以指定其他行为对信号作出反应：信号可以被忽略
- 程序可以设置一个信号处理函数，当信号发生时调用这个函数

**信号处理函数**
警告：  
	标准表示信号处理函数可以通过调用 `exit` 终止程序。用于处理除了 `SIGABRT` 之外所有信号的处理函数也可以通过调用 `abort` 终止程序。但是，由于这两个都是库函数，所以当它们被异步信号处理函数调用时可能无法正常运行。如果你必须用这种方式终止程序，注意仍然存在一种微小的可能性导致它失败。如果发生这种情况，函数的失败可能破坏数据或者表现出奇怪的症状，但程序最终将终止。
1. volatile数据
```c
/* 第1个测试 */
if (value) {
    printf("True\n");
} else {
    printf("False\n");
}
if (value) {
    printf("True\n");
} else {
    printf("False\n");
}
```
两段代码在 `value` 未被声明为 `volatile` 时，编译器可能认为 `value` 不变而进行优化，导致第二次 `if` 判断被裁剪或复用第一次的结果；若 `value` 可能异步改变（如中断、信号、硬件寄存器），应加 `volatile` 抑制优化。
就是不加`volatile`会导致上面代码实际运行是下面的样子：
```c
/* 第2个测试 */
if (value) {
    printf("True\n");
    printf("True\n");
} else {
    printf("False\n");
    printf("False\n");
}
```
2. 从信号处理函数返回
正常信号（除 SIGFPE 外）  
    从处理函数返回后，程序在“被中断点”继续执行；SIGFPE 不可返回，行为未定义。
重复捕捉  
    多数系统在调用处理函数前会把该信号重置为默认动作。若需继续捕捉，处理函数里必须重新调用 `signal()` 安装自己，否则只有第一次生效。
可移植性  
    信号集、是否自动重置、能否安全调用库函数等因平台而异；信号处理函数限制多、调试难。  
    → 只在真正需要时才用，并严格遵守“不调用非异步信号安全函数”等规则，可把移植风险降到最低。

## **执行环境**
**终止执行**`<stdlib.h>`
这三个函数与正常或不正常的程序终止有关 :
```c
void abort(void);
void atexit(void (func)(void));
void exit(int status);
```
- `abort` 函数用于不正常地终止一个正在执行的程序。由于这个函数将引发 `SIGABRT` 信号，可以在程序中为这个信号设置一个信号处理函数
- `texit` 函数可以把一些函数注册为退出函数（exit function）。当程序将要正常终止时（或者由于调用 `exit`，或者由于 `main` 函数返回），退出函数将被调用。
- `exit` 函数用于正常终止程序。如果程序以 `main` 函数返回一个值结束，那么其效果相当于用这个值作为参数调用 `exit` 函数。
**禁止在 `atexit` 注册的退出函数里再次调用 `exit`**，否则后果未定义——最可能的后果是形成无限递归，程序一直 `exit`→调用退出函数→再 `exit`→再调用退出函数……直到堆栈耗尽才停下来。

环境（environment）就是一个由编译器定义的名字/值对的列表，它由操作系统进行维护。

对那些当前版本暂时用不到、但又属于接口（头文件里声明过）的函数，不给出真正的功能代码，而是写一份“空壳”——**存根（stub）**——放在数组模块里。典型写法：

使用assert来防止非法操作，断言只能够对用户自己 也能够进行检查的内容进行检查。

	让 `create_stack` 返回一个状态值（如成功/失败标志），调用方发现失败后可主动把长度缩小再试一次，而不是直接“爆掉”。

## 实现的改进
**拥有超过一个的堆栈**
- **问题**：原实现将数据（数组和`top_element`）封装在模块内部，导致“一个程序便不能拥有超过一个的堆栈”。
- **改进方法**：将数据移出模块，通过参数传递给堆栈函数。用户可创建多个数组并通过调用堆栈函数将其作为堆栈使用。
- **风险**：失去封装性，“用户可以直接访问它”，可能导致非法访问和数据错误。同时，用户需确保传递正确的参数，“如果这些参数发生混淆，其结果就是垃圾”。
- **建议**：将堆栈数组和`top_element`捆绑在一个结构里来减少错误。
---
**拥有超过一种的类型**
- **问题**：存储值的类型在编译时固定，无法轻松支持多种类型（如整数堆栈和浮点数堆栈）。
- **解决方案**：
    1. **重复代码**：为不同类型编写堆栈函数的拷贝，但“大量重复代码”导致维护困难。
    2. **宏定义**：将整个堆栈模块实现为`#define`宏，以类型为参数生成代码，但需解决函数名冲突问题。
    3. **类型无关（`void *`）**：存储`void *`类型的值，通过强制类型转换实现。但“绕过了类型检查”，若类型错误会导致灾难性后果。
- **注意**：树模块实现类型无关更困难，需传递用户编写的比较函数指针，同样存在类型安全风险。
---
**名字冲突**
- **问题**：不同ADT的某些函数可能同名（例如堆栈、队列都有`is_full`和`is_empty`，队列和树都有`insert`），导致冲突。
- **解决方法**：采用命名约定，使函数名唯一且可接受，例如`is_queue_empty`和`is_stack_empty`。但“这些长名字使用起来不太方便”。
---
**标准函数库的 ADT**
- **背景**：由于上述3个问题，标准函数库未提供通用的ADT实现。
- **泛型模拟**：C语言本身不支持泛型，但可用`#define`宏近似模拟。例子：泛型堆栈宏，参数包括类型、后缀和数组长度。“后缀用于粘贴到由实现定义的每个函数名的后面，用于避免名字冲突”。
- **使用示例**：通过宏可创建不同类型堆栈（如整数堆栈和浮点数堆栈），但若需要多个同类型堆栈，会创建重复函数组。
**代价**：用户需承担多项责任，包括命名约定、确保只创建一组函数、使用正确函数名、传递正确数据结构等。
1. 采用一种命名约定，避免不同类型间堆栈的名字冲突。
2. 必须保证为每种不同类型的堆栈只创建一组堆栈函数。
3. 在访问堆栈时，必须保证使用适当的名字。
4. 确保向函数传递正确的堆栈数据结构。
**结论**：用 C 语言实现泛型是相当困难的，因为它的设计远早于泛型这个概念被提出之时。泛型是面向对象编程语言处理比较完美的问题之一
PS（泛型模拟后面避免冲突的依据）：
	**`##` 运算符**，C预处理器中的`##`运算符可以将两个标记（tokens）连接成一个新的标识符。

**寄存器变量**
这些编译器不会把字符型变量存放在寄存器中。在有些机器上，double 的长度太长，无法存放在寄存器中。有些机器具有特殊的寄存器，用于存放浮点值。
我们可以很容易地对测试程序进行修改来发现这些细节。
在许多机器上，**不管指针指向什么类型的东西，它的长度是固定的**。所以你可能会发现任何类型的指针都可以存放在寄存器中。

那么其他变量存放在什么地方呢？
	机器使用的地址模型执行间接寻址和索引操作。这种组合工作颇似数组的下标引用。
	寄存器 a6 称为帧指针（frame pointer），它指向堆栈帧内部的一个“引用”位置。
	堆栈帧中的所有值都是通过这个引用位置再加上一个偏移量进行访问的。
	如，a6@(-28) 指定了一个偏移地址 -28。
	注意偏移位置从 -4 开始，每次增长 4。这台机器上的整型值和指针都占据 4 个字节的内存。使用这些偏移地址，你可以建立一张映射表，准确地显示堆栈中的每个值相对于帧指针的位置。
为什么这些寄存器需要在函数序中进行保存？
	函数必须对任何将用于存储寄存器变量的寄存器进行保存，这样它们原先的值可以在函数返回到调用函数前恢复，这样就能保留调用函数的寄存器变量。

- 当值压入堆栈时，堆栈向低地址方向生长（向上）。
接下来的指令是一个“跳转子程序（jump subroutine）”。它把返回地址压入到堆栈中，当被调用函数结束任务后需要返回到它的调用位置时，就需要使用这个压入到堆栈中的返回地址。

**函数序**
紧接着上面，执行流来到了被调用函数的函数序。
link指令分为几个步骤：

**堆栈中的函数次序**
为什么参数要以它们在参数列表中的相反次序逐个压到堆栈中？
	被调用函数使用帧指针加一个偏移量来访问参数。
	当参数以反序压入到堆栈时，参数列表的第 1 个参数便位于堆栈中这些参数的顶部，它距离帧指针的偏移量是一个常数。
如果参数以相反的顺序压入到堆栈中又会怎样呢（也就是按照参数列表的顺序）？
	第 1 个参数距离帧指针的偏移量就和压入到堆栈的参数数量有关。
	编译器可以计算出这个值，但还是存在一个问题——实际传递的参数数量和函数期望接受的参数数量可能并不相同。
	在这种情况下，这个偏移量就是不正确的，当函数试图访问一个参数时，它实际所访问的将不是它想要的那个。
首个问题的答案 -- 也就是因为为了节约维护偏移量所耗费的系统资源。

**表达式的副作用**

表达式会被求值但不会对程序产生影响，因为它的结果并未保存。
实际上可以以一种微妙的方式对程序的执行产生影响。
```c
int f(int a, int b) {
    int x = a + b;
    return;   /* 遗漏了返回值表达式 */
}
```
这个函数计算一个结果但并不返回任何东西，因为这个表达式被错误地从 return 语句中省略。
使用这个编译器，这个函数实际上可以返回这个值。
d0 被用于计算 x，并且由于这个表达式是最后进行求值的，所以当函数结束时 d0 仍然保存了这个结果值。
之所以可能出现这些效果，其罪魁祸首是原先存在的那个错误——**return 语句省略了表达式**。
## C语言和汇编语言的接口
**你的环境肯定在某些方面与它不同！**
- 首先，汇编程序中的名字必须遵循外部标识符的规则。在这个系统中，它必须以一个下划线开始。
- 其次，汇编程序必须遵循正确的函数调用/返回协议。有两种情况：从一个汇编语言程序调用一个 C 程序和从一个 C 程序调用一个汇编程序。
**为了从汇编语言程序调用 C 程序：**
1. 如果寄存器 d0、d1、a0 或 a1 保存了重要的值，它们必须在调用 C 程序之前进行保存，因为 C 函数不会保存它们的值。
2. 任何函数的参数必须以参数列表相反的顺序压入到堆栈中。
3. 函数必须由一条“跳转子程序”类型的指令调用，它会把返回地址压入到堆栈中。
4. 当 C 函数返回时，汇编程序必须清除堆栈中的任何参数。
5. 如果汇编程序期望接受一个返回值，它将保存在 d0（如果返回值的类型为 double，它的另一半将位于 d1）。
6. 任何在调用之前进行过保存的寄存器此时可以恢复。

**为了编写一个由 C 程序调用的汇编程序：**
1. 保存任何你希望修改的寄存器（除 d0、d1、a0 和 a1 之外）。
2. 参数值从堆栈中获得，因为调用它的 C 函数把参数压入在堆栈中。
3. 如果函数应该返回一个值，它的值应保存在 d0 中（在这种情况下，d0 不能进行保存和恢复）。
4. 在返回之前，函数必须清除任何它压入到堆栈中的内容。
在你的汇编程序中创建一个完全 C 风格的堆栈帧并无必要。你所要做的就是调用一个能够以正确的方式压入参数并当它返回时能够正确地执行清理任务的函数。
在你实际编写汇编函数之前，你需要知道你机器上的汇编语言。一些简陋的能够让我们明白一个现有的汇编程序是如何工作的知识对于编写新程序是远远不够的。
## 运行时效率
程序增长后的容量超过了内存的数量时，它就无法运行，因此它就属于“太大”。
即使在一些现代的机器上，一个必须存储于 ROM 的程序必须相当小才有可能装入到有限的内存空间中。
虚拟内存是由操作系统实现的，它在需要时把程序的活动部分放入内存并把不活动的部分复制到磁盘中，这样就允许系统运行大型的程序。
	但程序越大，需要进行的复制就越多。所以大型程序不是像以前那样根本无法运行，而是随着程序的增大，它的执行效率逐渐降低。
所以，什么时候程序显得“太大”呢？就是当**它运行得太慢**的时候。

---
**提高效率**
现代的经过优化的编译器在从一个 C 程序产生高效的目标代码方面做得非常好。
因此，把时间花在对代码进行一些小的修改以便使它效率更高常常并不是很合算。
**提示：**  
	如果一个程序太大或太慢，较之钻研每个变量，看看把它们声明为 register 能不能提高效率，选择一种效率更高的算法或数据结构往往效果要满意得多。
然而，这并不是说你可以在代码中胡作非为，因为风格恶劣的代码总是会把事情弄得更糟。

从何处着手提高它的速度呢？
简单地说就是测算程序的每个部分在执行时所花费的时间。
- 花费时间最多的那部分程序显然是优化的目标。
- 程序中使用最频繁的那部分代码运行速度如果能更快一些，将能够大大提高程序的整体运行速度。

三个有趣的地方：
- 在耗费时间最多的函数中，有些是库函数。
但在重新设计程序时，如果能够不用或少用动态内存分配，程序的执行速度在最多情况下可以提高 25%。
- 有些函数之所以耗费了大量的时间是因为它们被调用的次数非常多。即使每次单独调用时它的速度很快，由于调用次数多，所以总的时间不少。
加上几个明智的 `register` 声明稍微提高函数的效率，对程序的总体性能可能还是会有较大的改善。
- 有些函数调用的次数并不多，但每次调用所花费的时间却很长。
为这个函数寻找一种更快的算法最多可以使程序的速度提高 7.75%。

**作为最后一招**，你可以对单个函数用汇编语言重新编码，函数越小，重新编码就越容易。
- 就是自己去改那个汇编后的文件，进行优化。
这种方法的效果可能很好，因为在小型函数中，C 的函数序和函数跋所耗费的固定开销在执行时间中所占的比例不小。对较大的函数进行重新编码要困难得多，因此把你的时间花在这个地方效率不是很高。

性能评测常常并不能告诉你原先不知道的东西，但有时候它的结果可能相当出人意料。性能评测的优点在于你可能弄清你正在花时间研究的那部分程序可能会带来最大程度的性能提高。
